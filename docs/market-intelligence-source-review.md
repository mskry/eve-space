# Market Intelligence ESI source review

Reviewed 2026-09-28 against the [live EVE API Explorer](https://developers.eveonline.com/api-explorer), which loads [`/meta/openapi.json`](https://esi.evetech.net/meta/openapi.json), and the generated `@evespace/esi-client` 3.x market operation descriptors at compatibility date `2026-08-18`. The deployed request setting defaults to `2026-08-23`, which resolves to `2026-08-18` in the [current compatibility-date list](https://esi.evetech.net/meta/compatibility-dates). All five operations have a minimum compatibility date of `2020-01-01` and are SDK-classified reads. The gateway owns credentials, validators, rate handling, and expiry; module code receives declared platform dispatch only.

| Operation                         | Endpoint and required input                                                                | Authority                                                                    | Documented freshness fallback               | Pagination and limit                                                     | Validators / rate                                                             |
| --------------------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| `GetMarketsRegionIdOrders`        | `GET /markets/{region_id}/orders`; `order_type=all\|buy\|sell`; optional `type_id`, `page` | Public                                                                       | 300 s                                       | 1-based `page`, response `X-Pages`; up to 1,000 orders observed per page | `ETag`, `Last-Modified`; `market-order` 12,000 tokens / 15 min                |
| `GetMarketsRegionIdTypes`         | `GET /markets/{region_id}/types`; optional `page`                                          | Public                                                                       | 600 s                                       | 1-based `page`, response `X-Pages`; 1,000 IDs observed per page          | `ETag`, `Last-Modified`; no route group declared, legacy error budget applies |
| `GetMarketsRegionIdHistory`       | `GET /markets/{region_id}/history?type_id=…`                                               | Public                                                                       | Daily 11:05 UTC, otherwise runtime metadata | No pagination                                                            | `ETag`, `Last-Modified`; no route group declared                              |
| `GetMarketsPrices`                | `GET /markets/prices`                                                                      | Public                                                                       | 3,600 s                                     | No pagination                                                            | `ETag`, `Last-Modified`; no route group declared                              |
| `GetMarketsStructuresStructureId` | `GET /markets/structures/{structure_id}`; optional `page`                                  | OAuth scope `esi-markets.structure_markets.v1` for the exact owned character | 300 s                                       | 1-based `page`, response `X-Pages`                                       | `ETag`, `Last-Modified`; no route group declared                              |

Each route accepts `If-None-Match` and `If-Modified-Since`, documents a possible `304`, and returns `Cache-Control`, `ETag`, and `Last-Modified` on success. Runtime `Expires` or usable `Cache-Control` takes precedence over the fallback above; neither an application retry nor a collection schedule may force a refresh before expiry. Offset pages have separate cache identities. A first-page `X-Pages` value describes only that response, not proof that subsequent pages form an atomic exchange snapshot. The collector must record each page's validation time, reject incompatible page-count drift, and publish only a complete bounded observation.

Public order records require `order_id`, `type_id`, `location_id`, `system_id`, `volume_total`, `volume_remain`, `min_volume`, `price`, `is_buy_order`, `duration`, `issued`, and `range`. Structure orders have the same required fields except `system_id`. Public daily history requires `date`, `order_count`, `volume`, `highest`, `average`, and `lowest`; the average is a historical statistic, not a median or executable quote. Prices require `type_id` with optional `adjusted_price` and `average_price`; adjusted price is an industry-cost input, not executable order depth. No public market route may expose structure order records.

The first-page samples below were followed by one complete The Forge book collection, with three concurrent page requests. The browser HTTP cache reused the previously fetched first page; no validator was forced before expiry.

The complete The Forge book returned 404,567 unique orders from 405 pages, 95,983,295 bytes of uncompressed JSON, and no observed duplicate ID or page-count disagreement. Three concurrent browser requests completed in 17.9 seconds. This is a network/payload benchmark, **not** a gateway/worker or PostgreSQL storage measurement; one run cannot establish a robust duration bound. Domain's first page implies up to 183,000 rows and roughly 44 MB but its complete collection was not measured. The watched Tritanium requests fit one page. A small region (`10000058`) returned 2,407 unique orders across three pages, with the final page holding 407 orders; all pages agreed on `X-Pages`. All sampled public responses carried an `Expires` boundary, ETag, and Last-Modified; the actual cache boundary must be read per response. Private structure content was not sampled without an eligible character token.

PLEX (`44992`) is absent from all 19,132 types in The Forge's active ESI market-type list; registered-gateway `all`, `sell`, and `buy` order reads for that region returned zero. The official Global PLEX Market (`19000001`) listed exactly `[44992]`, returned 998 orders on one public order page, and served 424 source history days. The reference browser downloads that pseudo-region too and special-cases PLEX by ignoring the selected region in `apps/store/items/orders/api.go`; its “PLEX in The Forge” title therefore shows global orders, not regional coverage. EVE Space keeps the global identity separate, restricts it to PLEX, and preserves its own observation and source clocks.

The reference EVE Market Browser's `apps/store/items/orders/orders.go` fetches pages sequentially and builds one replacement book before its `dbReplaceOrders` transaction; its own comment reports mid-batch order changes. `apps/store/hoardling.go` explicitly says its ten-minute timer should instead use ESI `Expires`. The shared ESI fetcher uses `X-Pages` but does not establish one upstream snapshot. This is useful layout and workload evidence, not authorization, cache, or publication policy for EVE Space. Our per-page gateway cache suppresses upstream requests while each representation is fresh; it does not remove the page/order/concurrency/storage ceilings or prove all pages are complete together.

## Initial limits and storage evidence

The first-page and full-book sample motivate an initial hard ceiling of 512 pages and 512,000 orders per observation, three concurrent page requests, one full-region profile, at most four configured public profiles, 16 watched types per watched profile, and 16 queued profile identities. A page count or order count beyond these limits is unavailable, never truncated and published. These are **initial admission ceilings**, not a claim that a 512-page profile can refresh within an upstream TTL. Actual worker/queue admission and rate/cooldown tests are still required before enabling a profile.

The supported regional allowlist is The Forge (`10000002`), Domain (`10000043`), and the measured small region `10000058`. The Global PLEX Market (`19000001`) is separately admitted only as a watched-type profile for exactly PLEX (`44992`) with no station filter; it is not a full-region collection candidate. A configured station must be an NPC station in the selected region according to the committed version-six SDE projection. Other IDs are rejected rather than treated as a valid market merely because they are positive numbers; expanding regional coverage requires a reviewed size and collection budget.

The profile-keyed planner now tests four configured profiles as a durable PostgreSQL ceiling (`market-profile-persistence.test.ts`), a maximum of 16 due identities per planning pass, queue high-water admission of only the available prefix (`profile-work-planner.test.ts`), and active/waiting Redis coalescing by resource, profile, and revision while ignoring a changed due timestamp (`worker-platform.test.ts`). Omitted work remains due in PostgreSQL; queue jobs carry only resource and profile identities, revision, and due time. The existing fixed-resource 32-request budget is unchanged, while a profile work identity is capped at 512 page requests and three in-flight pages. These are tested admission bounds; sustained production write throughput for a full Forge profile still requires the explicit low-volume rollout and monitoring below.

An isolated PostgreSQL 17 Testcontainer applied the proposed Market-module schema and inserted 1,000 representative numeric order rows with its primary and type/side/price indexes. `pg_total_relation_size` grew by **303,104 bytes**, or **303.104 bytes per order including index growth** (`market-storage-measure.test.ts`). At that density the measured 404,567-order Forge book requires approximately 123 MB of PostgreSQL order rows and indexes, excluding headers, pages, other indexes, WAL, table churn, and vacuum. One current and one prior book would occupy roughly 246 MB before those extras; continuous five-minute full-book replacement can generate tens of gigabytes of daily write traffic. These are extrapolations from a single representative page, not production disk or write-throughput measurements.

Initial retention policy: keep the current complete raw observation for as long as it remains current, even through collection failures; after successful replacement keep superseded raw observations for a **15-minute rollback horizon**, then delete them and failed staging. Retain compact derived metrics for **30 days**, daily history for **one year** where ESI supplies it, and hourly non-executable reference prices for **30 days**. Expose the actual available date/time range rather than suggesting older metrics still exist. At five-minute full-region refresh, a 15-minute horizon may temporarily retain three superseded books in addition to the current book; capacity planning must allow at least roughly 492 MB of measured-density order rows and indexes per such profile plus WAL/vacuum overhead. Enable only a measured low-volume profile first, monitor real gateway latency, PostgreSQL growth and queue age, and re-evaluate these ceilings before enabling The Forge full-region mode.
