# Character Transfer Engineering Inventory

This inventory defines the persistence, lock-order, and authorization-lifecycle constraints for
explicit cross-account character transfer. Transfer uses detach/recreate with a new subject
lifecycle; it does not update `characters.user_id` in place.

## Persistence And Retention

The transfer transaction removes ownership-bound disposable state, preserves independently retained
history, and retains an empty source user whenever account or actor attribution requires a live user.
Database cascade behavior is not permission to erase retained history.

| State                                                            | Database relationship                                                                        | Transfer and empty-source behavior                                                                                                                                                         |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `characters`                                                     | `user_id` cascades from `users`                                                              | Delete the source binding and recreate it for the fixed destination as non-main.                                                                                                           |
| `eve_tokens`                                                     | Cascades from `characters`                                                                   | Delete old ciphertext with the source binding. Insert only callback credentials for the new lifecycle, with a generation greater than the prior generation when one existed.               |
| `platform_subject_lifecycles`                                    | Character binding cascades from `characters`                                                 | Delete the old lifecycle and create a distinct lifecycle.                                                                                                                                  |
| `platform_collection_state`                                      | Cascades from subject lifecycle                                                              | Disposable and rebuilt for the new lifecycle by current-state planning.                                                                                                                    |
| `sessions`                                                       | Cascades from `users`                                                                        | Preserve sessions for nonempty accounts. Delete every session of an emptied source even when the user is retained.                                                                         |
| `oauth_states`                                                   | User and character references cascade                                                        | Disposable. Bound-session and lifecycle checks prevent already-consumed state from reviving an emptied source. Transfer state is consumed before callback mutation and cannot be replayed. |
| `organization_account_compliance`                                | Subject user cascades                                                                        | Recompute source then destination before optional cleanup. The projection is disposable only when the source user is eligible for deletion.                                                |
| `organization_compliance_issues`                                 | Account projection and optional composite character owner references cascade                 | Derived and disposable. Source issues are removed by detachment and regenerated by source compliance before cleanup.                                                                       |
| `organization_character_exceptions`                              | Composite source user/character reference cascades; approver and revoker references restrict | Character-specific projection does not transfer. Active or historical records may retain actor attribution; detachment must preserve required history or retain the source user.           |
| `organization_role_grants` and `organization_authority_evidence` | Grant subject cascades; grantor/revoker and evidence references restrict                     | Never transfer. Active evidence blocks transfer. Any retained grant or evidence requires retaining the empty source user.                                                                  |
| `organization_corporation_sources`                               | Current character reference becomes null on detachment; immutable evidence character remains | Never transfer. An active current-version source blocks transfer. Historical source records remain independently attributable and their actor references may retain the source user.       |
| `organization_group_assignments`                                 | Subject cascades; assigning/revoking users restrict                                          | Never transfer. Automatic compliance assignments are rebuildable; manual assignments and user actor attribution require retaining the source user.                                         |
| `organization_member_blocks`                                     | Subject cascades; blocking/unblocking users restrict                                         | Never transfer. A block or user actor attribution requires retaining the applicable user.                                                                                                  |
| Organization groups and permission bundles                       | Creator user references restrict                                                             | Never transfer. Creator attribution requires retaining the user.                                                                                                                           |
| `organization_audit_events`                                      | Actor, subject, and target identifiers intentionally have no user FK                         | Append-only and independently preserved. Compliance audit rows produced while recomputing an emptied source do not by themselves retain the user.                                          |
| `domain_events`                                                  | No user, character, or lifecycle FK                                                          | Append-only acceptance and replay history remains attributable from immutable payload snapshots.                                                                                           |
| Transfer previews                                                | Live source, destination, lifecycle, and administrator bindings                              | Short-lived and disposable. Expiry or stale bindings prevent approval creation.                                                                                                            |
| Transfer approvals                                               | Immutable identifier snapshots, no cascading source/destination user dependency              | Retained through source cleanup. Terminal approval state cannot be reactivated.                                                                                                            |
| Transfer audit                                                   | Immutable identifier snapshots and no live identity FK                                       | Append-only, secret-free, and retained independently of users, approvals, and domain-event retention.                                                                                      |
| Organization activity snapshots/checkpoints                      | No core FK; keyed by lifecycle, organization version, and authorization generation           | Historical rows can remain but are unreachable as current state after lifecycle rotation.                                                                                                  |

An emptied source user is eligible for deletion only when all known retention checks prove that it
has no elevated grants, manual governance decisions, account blocks, manual group assignments,
source registration history requiring a live actor, exception actor attribution, created group or
bundle attribution, or other restrictive dependency. Automatic compliance projections, automatic
group assignments, sessions, OAuth state, and newly produced non-FK compliance audit records do not
force retention. Unknown dependencies retain the user. The optional delete runs in a savepoint;
SQLSTATE `23503` retains the user, while every unexpected error aborts the transfer.

## Lock Order

All retries re-evaluate blockers in `main-character`, `authority-evidence`, then
`corporation-source` order. Bounded lock waits fail the operation atomically.

The approved redemption order is:

1. Read immutable approval identities without a row lock only to discover the lock targets.
2. Acquire the exclusive character advisory transaction lock.
3. Lock the current deployment organization version for compliance.
4. Lock source and destination user rows in ascending UUID order.
5. Lock the approval row, then the installation-level administrator-authority row.
6. Revalidate wall-clock expiration, revocation/consumption, approving administrator authority,
   destination session, fixed users, source lifecycle, current ownership, roster/main state, and
   blockers.
7. Detach/recreate ownership, lifecycle, and tokens without acquiring a resource lock.
8. Append source detachment then destination attachment events.
9. Recompute source then destination compliance while both user locks remain held.
10. Delete sessions for an emptied source, apply conservative user cleanup, consume the approval,
    and append consumption audit before commit.

Existing paths must remain compatible with that order:

| Path                                         | Required order or serialization rule                                                                                                                                           |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Login, attachment, reauthorization, deletion | Character advisory lock, organization version lock, then user row. Bound-user operations recheck the active session after the user lock.                                       |
| Main selection                               | User row lock. Transfer locks both users in stable UUID order before reading main state.                                                                                       |
| Token refresh                                | Character advisory lock, lifecycle/token reread, then organization/compliance work. A late refresh must compare lifecycle and generation before write.                         |
| Owner claim                                  | Organization version lock, character row, user and grant/evidence state. The character advisory boundary must serialize a claim with transfer.                                 |
| Corporation source mutation                  | Organization version lock, character/token row, then source row. Transfer rechecks active source state while the organization and character boundaries are held.               |
| Organization or policy change                | Organization version update lock, then affected users in ascending UUID order. Transfer's shared organization-version lock prevents old-version compliance.                    |
| Administrator authority change               | Installation authority row only; it remains independent of organization configuration and must not acquire approval state after changing authority.                            |
| Approval creation                            | Character advisory lock, organization version, users ascending, then preview/approval state. Recheck preview bindings and blockers.                                            |
| Approval revocation                          | Approval row only; never acquire character or user locks after it.                                                                                                             |
| Resource materialization                     | Resource advisory lock, module setting, shared character advisory lock, then lifecycle/generation eligibility and checkpoint state. Transfer never waits on the resource lock. |

## Authorization Lifecycle Boundaries

Lifecycle plus authorization generation is the correctness identity. Character ID alone is not an
authorization identity because ownership can transfer away and back.

| Boundary                                 | Required fence                                                                                                                                                                               |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Owned-character middleware               | Capture and pass the current `subjectLifecycleId` with the owned character.                                                                                                                  |
| Token readers                            | Require character ID plus lifecycle for character-authorized work.                                                                                                                           |
| Process-local collapsed refresh          | Key by lifecycle-bearing principal, not character ID alone, and reject a late result after lifecycle/generation change.                                                                      |
| Private L1/shared cache                  | Bind the authorization principal to lifecycle and validate generation for fresh and outage-stale envelopes. Redis eviction is only best effort.                                              |
| Direct character ESI reads and mutations | Use the lifecycle captured by ownership middleware and recheck it before returning or committing in-flight work.                                                                             |
| Resource-refresh jobs and batches        | Carry subject lifecycle and expected generation. Obsolete work exits before loading current-owner tokens or calling ESI.                                                                     |
| Materialization                          | Under the shared character advisory lock, recheck lifecycle and generation before snapshots or collection state are written.                                                                 |
| Collection state                         | Remains lifecycle-keyed and cascades with the old lifecycle. PostgreSQL current-state repair discovers the replacement lifecycle without event delivery.                                     |
| Module snapshots                         | Keep their original lifecycle/version/generation and never relabel retained history for the destination.                                                                                     |
| Browser query cache                      | Remove character-private entries on transfer success and refresh destination session, roster, compliance, and module state. Server lifecycle checks remain authoritative for other browsers. |
| Domain-event consumers                   | Use event-ID idempotency or converge from current durable ownership. Never remove current state by character ID in response to an old detachment event.                                      |

Affiliation work is public character state and may remain character-ID keyed, but any persistence that
attributes affiliation effects to a user must resolve current ownership at commit. Queue removal,
cache eviction, and paired event delivery order are not authorization mechanisms.

## Deployment And Rollback

Deploy the approval-aware API, worker, and web from one verified revision. The API must start first so
it can apply migrations `042_character_transfer_approvals.sql` and
`043_decouple_deployment_administrator.sql`; the worker must then accept that migration ledger before
the web exposes transfer controls. Do not create a mixed-version window in which ordinary attachment
can transfer cross-user ownership. After deployment, verify API and worker health, administrator
authentication, preview/create/inspect/revoke authorization, ordinary cross-user attachment refusal,
destination-bound transfer initiation, callback blocker feedback, source-session invalidation, and
current owned-resource access from both source and destination accounts.

Rollback is a forward-compatible application deployment, not a schema downgrade or an unmodified
pre-migration image. Retain migrations 042 and 043 in the migration manifest because startup rejects a
ledger containing unknown newer migrations. The rollback API must reject new transfer starts and all
outstanding transfer callbacks, continue rejecting ordinary cross-user attachment, and preserve the
approval and append-only audit tables. Deploy matching web handling that removes approval creation and
redemption controls and gives a generic safe failure for outstanding links. Pending approvals and
transfer OAuth state may remain for attribution and expiry, but cannot authorize mutation while the
rollback policy is active.

Already committed transfers remain authoritative. Rollback must not restore former ownership, source
sessions, old token ciphertext, authorization generations, subject lifecycles, compliance, cache
entries, snapshots, or queued work. Do not reverse a transfer with SQL or a database restore as a
routine feature rollback. If ownership must move again after transfer support is restored, use a fresh
approval bound to the current lifecycle, a current destination session, exact-character SSO proof, and
the normal locked eligibility checks.
